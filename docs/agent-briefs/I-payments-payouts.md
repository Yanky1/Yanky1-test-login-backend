## Product decisions (made by the product owner)
1. **Provider: Stripe Connect.** Build and test entirely in Stripe **test mode**; no real money. Keys only from config/env (`Stripe:SecretKey` / `STRIPE_SECRET_KEY`, `Stripe:WebhookSecret`), never committed. If no key is present, the app runs with a deterministic **fake provider** (dev/tests); CI never calls Stripe.
2. **Scope: seller side only.** Buyer checkout stays on the main website. The marketplace charges the buyer; the portal decides when seller funds become available and moves them to sellers. Model it as Stripe's **separate charges and transfers**: the marketplace's order/booking events carry the payment reference; the portal creates Transfers to the seller's connected account when funds are released, and Stripe pays out the connected account on its payout schedule.

## Features
1. **Payout onboarding:** a Stripe **Express** connected account per seller account (not per user), created on demand by an Owner; hosted onboarding via Account Links (identity/KYC, business details, bank account, tax info); return/refresh URLs; status synced from `account.updated` webhooks (details submitted, charges/payouts enabled, requirements currently due/past due, disabled reason). Show clear next steps when Stripe needs more information. An Express dashboard login link for the Owner.
2. **Ledger (source of truth for seller money), double-entry style, append-only, integer minor units + currency:** entries for sale (from orders/bookings: items, shipping, tax collected per policy), marketplace fee (from the platform fee setting), refunds and partial refunds, cancellation/no-show policy fees and booking extra charges, chargebacks/disputes (debit + dispute fee) and dispute wins (credit), reserves/holds, manual staff adjustments, transfers to the connected account, payouts (informational, from Stripe). Balances per seller account: **pending** (not yet releasable), **available** (releasable), **in transit/paid out**, **reserved**, and a negative balance when refunds exceed funds (recover from future sales; document the policy). Idempotent on source event ids; never edit or delete entries (corrections are new entries).
3. **Release rules:** funds for an order line become available N days (config, default 7) after delivery/completion and outside the return window rules in ORDERS.md; for bookings, N days after completion; refunds/returns before release reduce pending; account-level reserve % for new sellers (config) released after M days. A scheduled job computes releases and creates Transfers (batch per seller per day, minimum transfer amount), with retries and idempotency keys; transfers are paused when the seller is Suspended, payouts are disabled at Stripe, or a staff hold exists.
4. **Inbound contract (additive to the internal marketplace API, same HMAC scheme):** payment reference + amounts on order/booking ingest (or a separate `payment.captured` event), `refund.processed`, `dispute.created/updated/closed` from the marketplace; plus **Stripe webhooks** (signature verified with the endpoint secret, idempotent on event id, replay-safe): `account.updated`, `transfer.*`, `payout.*` (connected accounts), `charge.dispute.*` if the platform sees them. Document the contract in docs/PAYMENTS.md.
5. **Seller UI (frontend, after access):** sidebar "Payments": balance cards (pending, available, reserved, next transfer date), onboarding status and button, ledger/transactions table with filters (type, date, order/booking), drill-down to the order/booking, transfers and payouts history with status, monthly statements (on-screen + CSV, formula-safe; PDF optional), payout settings shown from Stripe (schedule, bank last 4 via Stripe, never full numbers), tax info status (Stripe handles 1099-K), disputes list with evidence due dates and a link to respond via the Express dashboard. WCAG 2.2 AA, responsive, light/dark, axe in E2E.
6. **Staff tools (backend only for now; admin screens are a separate workstream):** under the existing admin API and staff permission matrix: view a seller's balances, ledger and Stripe status; place/release a payout hold (reason, audit); manual adjustment credit/debit (Super admin, step-up, reason, audit, seller notified); retry a failed transfer; list failed transfers/payouts and accounts with requirements past due.
7. **Notifications:** email Owners (and opted-in Admins) when onboarding needs action, a payout fails, a dispute opens, a negative balance occurs, a staff adjustment happens.

## Security & correctness
- **Permissions:** Payments are visible to Owner and Admin; only Owners start/continue onboarding and open the Express dashboard; Managers and Viewers have no payments access by default (extend the central permission matrix and document it). IDOR: other accounts' payment data → 404.
- No card or bank numbers stored; only Stripe ids and last-4 from Stripe. PII masked in logs. Secrets only from config/env; separate test/live key handling; production refuses to start with a test key unless explicitly allowed.
- Money is integer minor units; currency stored on every entry; no floats; rounding rules documented (fees rounded half-up per line, documented).
- Concurrency: releases and transfers are race-safe (unique idempotency keys, DB constraints, claim/lease for the job; safe with multiple instances on PostgreSQL); webhook processing idempotent and order-independent (an older event can't overwrite newer state).
- Reconciliation job: compares ledger transfers with Stripe (fake in tests) and flags mismatches for staff.
