## 1. Marketplace integration (how orders arrive and how updates go back)
- **Inbound:** an internal service-to-service API for the main website, e.g. `POST /api/internal/v1/orders` (create), plus endpoints/events for buyer cancellation requests, return requests, delivery confirmations and buyer messages. Authenticate with HMAC-SHA256 request signing (shared secret from config/env, timestamp header, 5-minute window, replay protection by nonce or idempotency key); reject anything unsigned/stale/replayed. This API is separate from seller auth and is never callable with a seller token. Idempotent on the marketplace order id.
- **Order splitting:** one marketplace order can contain items from several sellers and brands. Create one SellerOrder per (seller account, brand), each with its own number (e.g. `SO-2026-000123`) and a reference to the marketplace order id. Reject lines whose product/variant/SKU doesn't belong to that account/brand or isn't Active.
- **Inventory:** on ingest, reserve/decrement stock through the existing inventory service (concurrency-safe). If stock is short, still accept the order but flag it "Oversold – needs attention". Release/restock on cancellation and (optionally, seller choice) on return received.
- **Outbound:** every seller-side change (accepted, shipped + tracking, delivered, cancelled + reason, refund issued, return decision, seller message reply) is written to a transactional OUTBOX and delivered to the marketplace webhook URL (config) with HMAC signing, retries with exponential backoff, and a dead-letter state visible to admins. Provide a dev/test sink. Money movement (charging, payouts, refunds) is done by the marketplace; the portal only records seller decisions and amounts.
- **Simulator:** a Testing/Development-only "Create test order" endpoint and a small dev page/script that generates realistic orders for the signed-in seller's products (single/multi-item, multi-brand split, variants, out-of-stock), and simulates buyer events (cancel request, return request, delivered, message). Disabled in Production (test it).
- Document the integration contract (payloads, signing, idempotency, outbox events) in docs/ORDERS.md so the main website team can implement it.

## 2. Order model and lifecycle
- **Data:** SellerOrder (account, brand, number, marketplace order id, placed at, currency, buyer display name, shipping address and shipping method/speed, ship-by and deliver-by dates from product handling time + method, gift message, status, flags), OrderLine (product/variant ids plus a SNAPSHOT of title, SKU, options, image, unit price, quantity, discounts, tax), money totals (items, shipping charged, tax, discounts, marketplace fee from config %, seller net), Shipment (carrier, service, tracking number, shipped at, lines and quantities), Cancellation, ReturnRequest (lines, reason, buyer comment, status, refund amount), Refund (full/partial, per line + shipping), OrderNote (internal), OrderMessage (buyer ↔ seller thread), and an OrderEvent timeline. Store money as decimal minor-unit-safe values; never float.
- **Statuses:** New (awaiting acceptance; configurable auto-accept) → Accepted/Processing → Partially shipped → Shipped → Delivered → Completed (after the return window). Side states: On hold, Cancelled (by seller with a reason, or buyer request approved), Return requested → Return approved/rejected → Return received → Refunded (full/partial). Enforce allowed transitions in one state machine; invalid ones return 409 with a clear message.
- **SLA:** ship-by countdowns, "Late" flags, a late-shipment and cancellation rate on the dashboard.
- **Buyer privacy:** store only what fulfilment needs (name, shipping address, optional phone for the carrier); buyer email is a marketplace relay address, never the real one. Mask buyer PII in logs. Redact the shipping address N days after completion (config, default 90) and document it.

## 4. Security and permissions (OWASP ASVS L2)
- Every seller endpoint checks active-account membership AND brand scope (orders belong to one brand); other accounts' orders return 404 (no IDOR).

- Internal API: HMAC verification, idempotency, size limits, schema validation, no seller-token access; outbox signing secret separate from the inbound one; secrets only from config/env.
