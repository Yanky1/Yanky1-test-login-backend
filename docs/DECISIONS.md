# Decisions (spec gaps resolved by security standards)

| # | Topic | Decision | Basis |
|---|---|---|---|
| 1 | Tokens | JWT access token (RS256, `kid`, iss/aud/lifetime validated, zero clock skew, 60 min) with `sid` claim; each request also checks the session row (revoked/idle). | OAuth BCP, ASVS 3.x |
| 2 | Refresh tokens | 256-bit opaque, stored as SHA-256, rotated on every use; reuse of a used token revokes the whole session/family and is audited; bound to a `UserSession`. 30-day absolute lifetime, idle limit server-side. | OAuth BCP §4.14 |
| 3 | Browser storage | Access token only in JS memory. Refresh token delivered as `sl_rt` cookie: HttpOnly, Secure, SameSite=Strict, `Path=/api/v1/auth`. The body still contains `refreshToken` for contract compatibility (non-browser clients); the SPA ignores it. | ASVS 3.4 |
| 4 | CSRF on refresh/logout | Cookie-authenticated requests need double-submit `X-CSRF-Token` (value of the readable `sl_csrf` cookie) **and** an allow-listed `Origin` (when present). Body-token requests (no cookie) skip CSRF because they are not ambient. | OWASP CSRF cheat sheet |
| 5 | Same site | SPA and API are expected on one site (Vite proxy in dev, reverse proxy in prod) because the cookie is SameSite=Strict. | |
| 6 | Login failures | Counted per HMAC(normalized submitted email), whether or not the account exists. 3 failures → hint "2 tries left"; 4 → "Last try" + Turnstile required; 5 → locked 15 min (lock check precedes password check, so a correct password is refused while locked). Real accounts additionally: all sessions revoked + Locked email. Counter resets on success, password reset, or 15 min without failures. | OWASP Auth cheat sheet |
| 7 | Failure body | `401 {"error":"Login failed"}` plus a separate `hint` object (`attemptsRemaining`, `lastTry`, `captchaRequired`, `lockedUntil`, `message`) derived **only** from the counter, so it is identical for real and non-existent accounts. After a correct password on a 2FA account the 401 also carries `twoFactorRequired:true` (only revealed once the password is proven). Captcha failure → `400 {"error":"Verification failed"}`. | ASVS 2.2 |
| 8 | Per-IP limits | ASP.NET rate limiter, fixed window per IP: `auth` (20/min) and `sensitive` (10/min) policies, 429 ProblemDetails. | |
| 9 | `accountStatus` | Always `"Active"` on success (unverified accounts can no longer sign in, see 26). Seller approval status is *not* in the login body; use `GET /seller/application`. | |
| 10 | Sign-in allowed for | Sellers whose status is not Rejected/Suspended, and Admin-role users (seeded from config). Rejected/Suspended → generic 401 and sessions revoked on change. | |
| 11 | Seller status | Separate `seller_accounts` table with an explicit transition table (Draft→PendingReview→NeedsInfo/Approved/Rejected, Approved→Live/Suspended, …). Admin API `POST /admin/sellers/{id}/status` (role `Admin`); each change audited; emails: Application received, Approved, Needs info, Not approved. | |
| 12 | Signup | See 26: `202` with no session; the session is created only by `verify-email`. | |
| 13 | Email codes | 6 digits, HMAC-hashed, 10 min expiry, 60 s resend cool-down, 5 attempts then the code is dead. | NIST 800-63B §5.1.3 |
| 14 | Password policy | ≥10 chars with upper/lower/digit/symbol, common-password list + trivial/ email-name checks; optional HaveIBeenPwned k-anonymity check (`Passwords:CheckPwned`, fails open if unreachable). | NIST 800-63B |
| 15 | Reset links | Identity data-protection tokens, 30 min, invalidated by the security-stamp change (single use). Success → unlock, revoke all sessions, Password-changed email. Reset also marks the email as verified. Keys must be persisted in production. | |
| 16 | Google/Apple | OIDC code flow + PKCE + state + nonce via ASP.NET OpenID Connect handler; result handed to the SPA via a one-time 2-minute code (no tokens in URLs). Link only when provider email is verified; creating a new account requires accepting Terms (`terms=1`). Linking to an *unverified* local account strips its password and sessions first (pre-hijacking defence). Last sign-in method can't be removed. Apple behind `ExternalAuth:AppleEnabled`. | OAuth BCP |
| 17 | Passkeys | .NET 10 built-in Identity passkeys (`SignInManager.MakePasskey*/PerformPasskey*`), discoverable credentials, RP ID/origins configurable. Options endpoint never reveals whether an email exists. | WebAuthn L3 |
| 18 | Redirect-back | Same-origin relative paths only (`SafeRedirect`: must start with a single `/`, no `//`, `\`, scheme or control chars); enforced in the SPA and for the external-login `returnUrl`. | |
| 19 | Idle logout | Frontend: warning with countdown from `config.json`; on expiry it calls logout (revokes server session). Backend: server idle limit (`Session:IdleTimeoutMinutes`) enforced on every authenticated request and refresh. Background refresh runs only after recent user activity. | |
| 20 | Data stores | PostgreSQL migrations (Postgres-specific), SQLite via `EnsureCreated` for dev/tests. All timestamps UTC `DateTime`. | |
| 21 | Certificates | ≤5 MB, extension allow-list + magic-byte sniff must agree, random storage key, `IFileStorage`, served as attachment with `nosniff`, owner only. | OWASP File Upload |
| 22 | Audit log | `AuditEvents` table (type, user, masked email, IP, detail); no passwords/tokens/codes. No viewer UI. | |
| 23 | Logging | Framework logging only; no request bodies; emails log kind/provider, never content. | |
| 24 | SMS | `ISmsSender` interface only. Opt-in stored as timestamp + wording version; nothing is sent. | |
| 25 | Test emails | `/api/test/emails` exists only when `ASPNETCORE_ENVIRONMENT=Testing`. Turnstile test stub (`Turnstile:UseTestStub`) emulates Cloudflare's documented dummy secrets offline; never enable outside Testing. | |
| 26 | Sign-up without enumeration or unverified sessions | `POST /auth/signup` and `/auth/signup/passkey/complete` always answer `202 {message, resendAfterSeconds}` and set no cookie, whether the address is new, unverified or already registered. New address → verification code mail. Existing *verified* account → nothing changes, the owner gets a "someone tried to sign up" mail. Existing *unverified* account → the latest sign-up replaces it (account deleted and recreated), so a squatter's password/passkey dies. The session is created by `POST /auth/verify-email {email, code}` (public, rate-limited, identical generic failure for unknown/verified/expired/wrong codes). Resend is `POST /auth/resend-code {email}`, always `202`. Login and passkey sign-in refuse unverified accounts. Residual: an attacker who re-signs-up in the seconds between the owner's sign-up and code entry could win the password; the code mail still only reaches the owner. | ASVS 2.5/2.2, pre-hijacking research |
| 27 | Claiming an unverified account | `AccountSecurityService.WipeCredentialsAsync`: removes passkeys, external logins, TOTP key, recovery codes, 2FA flag (and the password for provider claims), revokes sessions, rotates the security stamp. Called when a password reset completes on an unverified account and when Google/Apple claims one. Passkey add, 2FA setup/enable/disable/recovery codes and email change require the `VerifiedEmail` policy. | |
| 28 | Passkey sign-up binding | The email is the attested user entity's name; `/signup/passkey/complete` rejects an email that differs from it. | WebAuthn L3 |
| 29 | MFA parity for passkeys and providers | Passkeys use `userVerification: required` (also enforced server-side via `IsUserVerified`): possession + biometric/PIN is treated as satisfying MFA, so no extra TOTP. Google/Apple: when TOTP is on, `/auth/external/exchange` answers `401 twoFactorRequired` (the one-time code stays valid for its 2 minutes) and needs `totpCode`/`recoveryCode`; wrong codes count toward the same per-email lockout. | NIST 800-63B AAL2 |
| 30 | Step-up for passwordless email change | Accounts without a password must first confirm a 6-digit code mailed to the CURRENT address (plus a TOTP code if 2FA is on) before the new address gets its code. Password accounts still re-enter the password. | ASVS 2.7 |
| 31 | Atomic lockout | The attempt is *reserved* with one `UPDATE … RETURNING` (insert on first sight, retry on PK conflict) **before** the password is checked; reservations above `MaxFailures` are refused without checking anything, so parallel guessing cannot exceed 5 checks. A correct password on a 2FA account releases its reservation. | |
| 32 | Refresh grace window | The just-rotated refresh token is accepted for `Session:RefreshGraceSeconds` (30 s) and answered with a fresh pair (covers several tabs racing); older replays still revoke the whole session. Trade-off: a token stolen and replayed within those 30 s is also served. | OAuth BCP leeway |
| 33 | Multi-tab behaviour (frontend) | Activity and logout are shared across tabs (BroadcastChannel, `storage`-event fallback); the logout is performed by one tab under a Web Lock, the others follow; refreshes run under the `solvelt-refresh` Web Lock. | |
| 34 | Phone channel model | One verified E.164 number per account (unique index) + a 6-digit PIN hashed with the Identity hasher. Caller ID/SMS sender never authenticates: sign-in = PIN (caller ID matches) or SMS code to the account's number + PIN. Attempts use the web's per-account counter (3/4/5) and lockout mail; unknown numbers use a `phone:<number>` key so behaviour is identical. Captcha (4th failure on the web) is not applicable: keypad entry plus a texted code is the human/ownership check. | NIST 800-63B (out-of-band), ASVS 2.x |
| 35 | Webhook hardening | HMAC-SHA1 signature (Twilio/SignalWire scheme) over the exact public URL (`Phone:PublicBaseUrl`) + sorted form, constant-time compare, 403 otherwise; per-IP and per-number limits; voice `seq` on each step (stale/replayed step = repeat prompt), SMS `MessageSid` stored once. | Provider docs, OWASP |
| 36 | AI is language-only | Deterministic `PhoneEngine` decides everything; model proposals come from a fixed allowlist, validated against the current step; secrets are never sent (redaction + secret steps skip the model); emails are parsed deterministically so the model never sees them (deviates from "the model normalises spoken emails" for privacy); `say` text filtered; fallback to keypad/help with a distinct `ai.unavailable` audit. | OWASP LLM01/LLM02 |
| 37 | SMS text of an email | The voice sign-up texts the **masked** address (`j***@gmail.com`) for confirmation: the spoken read-back + keypad "1" is the actual confirmation, and full emails never travel by SMS. | Data minimisation |
| 38 | Legal consent by phone | Terms: explicit "1"/"YES" after the URL is read/texted; `TermsVersion` + time stored. Seller Agreement and certificate: on the web via the texted link (needs the full text). SMS marketing opt-in is not collected by phone (codes/links are "requested" messages). | E-SIGN-style explicit consent |
| 39 | Account usable only after email verification | Phone sign-up creates the account unverified (no password); it can sign in (web or phone) only after the emailed 6-digit code is entered (by keypad/SMS or on the web); a verified-email collision is answered like the web (mail to the owner, same prompts). A "finish on the web" link sets the password. | Same as #26 |
| 40 | SMS compliance | STOP/UNSUBSCRIBE/CANCEL/END/QUIT/STOPALL, HELP/INFO, START/UNSTOP run before state and AI; STOP blocks all outbound (codes too) until START; carrier STOP (21610) is mirrored. Non-requested messages need the stored seller opt-in. | CTIA / 10DLC |
| 41 | Links by SMS | Opaque 192-bit token (hash stored), single use, 30 min; reset links carry the Identity reset token (protected), signup links carry the chosen PIN hash (protected). Redeemed by the SPA at `/l/<token>`. | |
| 42 | Phone sessions | Authenticated phone/SMS "sessions" are rows in `phone_states` (10/15 min) and are not JWT sessions; "sign out of all devices" revokes the web sessions. | |
| 43 | No transcripts | Nothing the caller says is persisted; audit rows hold action names and masked numbers. | Privacy |
| 44 | Memberships | One user can belong to many seller accounts (`account_memberships`, unique per user+account) with a role; `SellerAccount.UserId` stays as the primary owner for legacy paths but is not used for authorization. Idempotent startup backfill gives each existing account an Owner membership + default brand. | Least privilege, backward compatibility |
| 45 | Roles | Owner / Admin / Manager / Viewer from one central permission matrix (`Teams/Permissions.cs`, docs/TEAMS.md). Business/legal details and seller-agreement are Owner-only (wizard stays unchanged for the Owner); Admins manage members (not Owners) and brands; ≥ 1 active Owner always; nobody edits themselves or anyone above their own role. | ASVS 4.x |
| 46 | Active account per session | Stored on the session; auto-selected when unambiguous, else last used, else the client must choose. Access token carries `acc`/`arole` as hints only; membership, role, scope and account status are re-read from the DB on every request, so removal/demotion applies immediately (no 401 loop: account endpoints answer 403 `no_active_account`). | Immediate revocation |
| 47 | Login contract | Original fields kept; `sellerId`/`vendorName` describe the active account; `accounts[]` and `activeAccountId` added. Top-level `accountStatus` keeps its original sign-in-state meaning (DECISIONS #9, existing tests); approval status per account is `accounts[].accountStatus`. Sign-in is refused only when every account is Rejected/Suspended; zero accounts may sign in. | Compatibility |
| 48 | Invitations | 256-bit token, SHA-256 stored, single use, 7 days, resend rotates the link, duplicate invite updates the pending one; per-account (30/h) and per-inviter (20/h) throttles; uniform 202 so responses never reveal whether the email has a login. Email changes nothing about the invitee's own credentials. | OWASP enumeration |
| 49 | Email proof for invitees | A new invitee proves mailbox possession with the invite link itself (delivered only to that mailbox, single-use, short-lived); account is created verified and skips the wizard. Existing verified logins must sign in (2FA/lockout apply) and their verified email must match the invited one. Passkey/Google at join deferred. | NIST 800-63B §5.1.3 reasoning |
| 50 | Brands | Per account, unique case-insensitive name, logo = JPEG/PNG/WebP ≤ 1 MB by magic bytes + extension match, random storage key, `nosniff`. Out-of-scope/other-account brands are 404. `RequireBrandAccess`/`BrandsFor` are the only sanctioned brand queries (products will use them). | IDOR |
| 51 | Ownership transfer | Owner only, step-up re-auth (password, or mailed code for passwordless accounts, plus TOTP when enabled); the previous Owner becomes Admin; both notified. | ASVS 2.7 |
| 52 | Caller ID never changes the prompt (supersedes the "known caller ID: PIN only" shortcut of #34) | Review finding: a different first prompt for registered caller IDs lets anyone (caller ID is spoofable) test whether a number is registered. Every caller is asked for the account's number, then gets the SMS code, then the PIN. | OWASP ASVS 2.2 |
| 53 | Phone credentials attach after email verification | Review finding (pre-hijack): number + PIN chosen in a phone/link sign-up are held in `phone_links` (`phone-pending`, 24 h) and attached when the mailbox is proven (`/auth/verify-email` hook or the emailed code by phone). `WipeCredentialsAsync` / `DeleteUnverifiedAsync` delete the held data and any number/PIN. | Same as #26/#27 |
| 54 | First phone number needs step-up | Password; passwordless accounts confirm with a code emailed to the account (then SMS code to the current number for later changes). A stolen session alone cannot attach an attacker's number. | ASVS 2.7 |
| 55 | Phone sessions follow web session revocation | `SessionService.RevokeAllAsync` also clears `phone_states.UserId/AuthUntil`; number removal deletes the user's phone states; the phone "sign out of all devices" ends the phone session too. | |
| 56 | Voice step claim | `UPDATE … WHERE Seq = @seq` claims a step atomically before the engine runs; parallel duplicates become stale replays. | |
| 57 | TwiML is UTF-8 | The XML declaration says utf-8 (writer over a UTF-8 `StringWriter`), matching the bytes sent. | |
