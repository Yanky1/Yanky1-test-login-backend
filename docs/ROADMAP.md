# Roadmap (out of scope for this iteration)

Each item lists a short design note so it can be added later.

* **Staff admin: impersonation / "log in as"** - not built on purpose. Design note: a short-lived (<=15 min), single-seller *impersonation token* minted only for Super admin with step-up and a ticket reason, carrying an `act` claim (`sub` = seller user, `act.sub` = staff id), read-only by default (writes need a second explicit "allow writes" step-up), never allowed for staff or other Super admins, shown with a permanent banner, every request audited as `admin.impersonation.*`, and revoked on staff logout.
* **Staff admin: SSO for staff** - OIDC (Entra/Google Workspace) with `amr` containing a second factor, mapped by group claim to `StaffRole`; keeps the staff session kind, step-up and IP allowlist, replaces the password+TOTP form.
* **Staff admin: passkeys as the staff second factor** - an `admin/auth/passkey/*` ceremony that mints a `Kind=staff` session with `MfaAt` (user-verified passkeys are already treated as two factors in `IdentityPasskeyOptions`).
* **Staff admin: four-eyes approvals** - `PendingAdminAction(kind, payload, requestedBy, reason)`; close account, ownership transfer, 2FA disable, dead-letter discard and fee changes need a second Super admin to approve (cannot be the requester) before they apply.
* **Forced re-acceptance of new Terms / Seller Agreement** - on bump, compare `SellerAccount.TermsVersion/SellerAgreementVersion` with the platform version at sign-in and route to an acceptance screen; the admin settings page already counts affected sellers.
* **Moderation extras** - reported product Q&A, automatic hold of listings with N open reports, appeal flow for hidden listings.
* **Business switcher / multi-brand** – split `SellerAccount` into `Organization` + `Brand`, add membership table; token carries active `org` claim and a `switch` endpoint reissues it.
* **Shop staff invitations and roles** – `Membership(userId, orgId, role)` + signed single-use invitation tokens by email; role claims scoped per org.
* **Guest mode** – anonymous browsing token with read-only scope; the placeholder `/guest` route is the entry point.
* **Account picker** – remember last N accounts per device (non-secret hints in a cookie) and drive `login_hint`/passkey allow-lists.
* **Seller presence / online status** – SignalR hub or heartbeat endpoint updating `LastSeenAt`; expose via cached query.
* **Onboarding checklist** – `OnboardingTask` rows per seller, evaluated by status events, rendered on the dashboard.
* **SMS features (phone verification, new-device code, trusted devices, New sign-in email)** – implement `ISmsSender` (Twilio/etc.), store verified phone, add device fingerprint cookie + `TrustedDevice` table, challenge when unknown, send "New sign-in" email via a new template. Consent timestamps already stored.
* **Magic link / email code login** – reuse `OneTimeCodeService` with purpose `login`, same throttle and captcha rules, no enumeration (generic response).
* **Save-and-resume reminders after 3 days** – background `IHostedService` querying drafts untouched ≥3 days; send reminder email once with deep link to the wizard step (`DraftStep`).
* **Buyer storefront (products) – DONE in part:** the signed catalog feed, images, events and question intake exist (`docs/CATALOG.md`); still open: a public unauthenticated read API and search index. Original note – public read API over Active products only (`descriptionHtml`, current price, images through a CDN-signed URL), search index fed from `products` (+ `SearchTerms`), question submission replacing `/api/dev/questions` (rate-limited, moderated into `ProductQuestion`).
* **Orders and payments** – workstream E: order lines reference `(ProductId, VariantId?, Sku)` and use `IInventoryService.Reserve/Commit/Release`; payments via a provider-agnostic `IPaymentProvider`.
* **Reviews** – `ProductReview(productId, orderLineId, rating, text, state)` created only from delivered order lines; seller reply like question answers; aggregates denormalised onto `Product`.
* **Advertising / sponsored listings** – `Promotion(productId, budget, bid, window)` + ranking hook in the search index; never mixes into seller catalog tables.
* **External marketplace / store sync – DONE for the Solvelt marketplace** (`CatalogVersion` is the feed cursor, `listing.*` events; `docs/CATALOG.md`); still open for third-party connectors. Original note – outbox of product change events (`Version` is the cursor) consumed by connector workers; per-connector field mapping.
* **Image import by URL** – server-side fetch is an SSRF risk; if added: allow-listed schemes/hosts, resolved-IP checks, size/time caps, run in a sandboxed worker, then the same `ImageProcessing` pipeline.
* **Multi-currency, tax classes, bundles, per-variation shipping, bulk edit of attributes, CSV variations** – follow-ups on the existing model.
* **Shipping labels / carrier rate shopping** (orders) – `IShippingProvider` (rates + label purchase + void) behind the ship dialog placeholder; store label URL and cost on `Shipment`; deduct label cost from seller net via a marketplace event.
* **Live carrier tracking polling** – a worker polls carriers (or a tracking aggregator webhook) for open `Shipment`s and drives `order.delivered`/delay events through `BuyerEventService.DeliveryAsync`; keep the manual "mark delivered" as fallback.
* **Buyer storefront, payment processing, payouts, marketplace fee invoicing** – belong to the main website; the portal already exposes amounts (`feeCents`, `netCents`, `refund.issued`) for a payout ledger (`Payout(sellerId, period, orders, fees, refunds)`).
* **Multi-warehouse inventory** – `StockLocation` + per-location `Reserved/Stock`; `IInventoryService` gains a location argument; ship dialog picks the location.
* **Fulfilment by the marketplace** – new `FulfilledBy` on `SellerOrder`; seller actions disabled, inbound shipment events from the marketplace WMS.
* **Multi-node live updates** – replace the in-process `EventHub` with Redis pub/sub or PostgreSQL LISTEN/NOTIFY.
* **Business-day SLA calendars and per-method transit times**, **multiple open returns per order**, **buyer-visible attachment scanning (AV)**.

* **Two-way Google / Outlook calendar sync and importing external calendars** (services) - OAuth app per provider (`CalendarConnection(membershipId, provider, refreshTokenEncrypted)`), push provider bookings as events, and read free/busy (never event bodies) into `CalendarBlock(Kind=Busy, Source=external)`; needs OAuth credentials and server-side fetching of remote content (SSRF review) which is why only the private ICS export exists now.
* **Auto-created video meetings (Zoom / Meet / Teams)** - `IMeetingProvider.CreateAsync(booking)` returning a join URL stored on the booking and revealed in `booking.confirmed`; replaces the manually entered link.
* **Group classes / multi-attendee capacity** - `Service.Capacity` + `Booking.Seats`; the slot engine counts seats instead of blocking the footprint, a `Session` entity groups bookings of one class.
* **Recurring bookings / subscriptions** - `BookingSeries(rrule, until)` that materialises bookings through the same create path (each occurrence takes the calendar lock); marketplace owns the billing.
* **Route-optimised travel time** - replace the fixed travel buffer by a distance-matrix call between consecutive at-customer jobs of a provider/day (`ITravelTimeProvider`), keep the buffer as fallback.
* **Payments and payouts for services** - belong to the marketplace; the portal already emits the amounts (`booking.cancelled`, `booking.no_show`, `booking.additional_charge_requested`, `booking.completed`).
* **Buyer-side booking UI** - part of the main website; consumes the signed availability/hold/confirm API.
* **Booking threads in the Messages inbox** - move `booking_messages` into E's `Conversation` model (`ConversationKind.Booking`) once the order workstream is stable.

* **Assistant: staff tools** (`/admin`) - a second `ToolRegistry`/`ActionDef` set for support staff on the same engine (approve seller applications, add notes, look up orders across accounts with explicit staff permissions); needs a staff `AccessContext`, its own system prompt, and conversations with `Surface=admin`.
* **Assistant: voice** - reuse the phone/IVR layer: speech -> `AssistantEngine` with a short-answer prompt and the read-only tool subset, confirmations by spoken PIN step-up (never "yes" alone).
* **Assistant: proactive suggestions** - a nightly job computes "late orders", "unanswered messages", "listings below 60 quality" per account and surfaces them as dismissible cards in the portal; actions still go through confirm cards.
* **Assistant: refunds** - `propose_refund` limited by `OrderRefund` permission and `Orders:ManagerRefundLimitCents`, high-risk card with the full amount breakdown and a second confirmation for amounts above a threshold.
* **Assistant: model streaming and cost controls** - stream tokens from the Claude API to the SSE channel, `claude-haiku-5-5` routing for simple read-only questions, prompt-cache hit-rate metrics, per-account monthly spend caps and a staff dashboard over `assistant_usage`.
* **Assistant: attachments and bulk work** - "fix all my drafts" as a batch card with per-item diffs; image alt-text suggestions from product photos.

* **Payments: buyer checkout / payment capture** - belongs to the main website; the portal only receives `payment.captured`. If ever moved here: PaymentIntents on the platform account with `transfer_group`, SCA/3DS handled by Stripe Elements.
* **Payments: multi-currency conversion** - the ledger is already per currency (balances, transfers and statements split by currency); missing: FX quotes, settlement currency per connected account (`default_currency`), and showing a converted total.
* **Payments: instant payouts** - Express accounts can request instant payouts in the Stripe dashboard; to expose them here add a `PayoutPolicy` (eligibility, fee passed to the seller as a `payout_fee` journal) and `POST .../payouts/instant`.
* **Payments: invoicing marketplace fees as tax documents** - generate a monthly fee invoice per seller from `Fees` entries (`FeeInvoice(sellerId, period, number, netCents, taxCents)`), numbering and VAT/GST per jurisdiction.
* **Payments: VAT/GST engines** - plug a tax provider behind the sale posting (`ITaxService`), record collected tax as a memo account and remittance reports.
* **Payments: in-portal dispute evidence upload** - `POST disputes/{id}/evidence` mapped to Stripe `dispute.evidence` fields with file uploads; for now the Express dashboard link is used.
* **Payments: PDF statements** - render the monthly statement (already computed by `statements/{month}`) with a server-side PDF library; CSV and on-screen exist.
* **Payments: per-line release and partial release** - release only the delivered shipments of a partially shipped order (needs per-shipment ledger attribution).
* **Payments: staff screens** - admin UI over the existing `/api/v1/admin/payments` endpoints (separate workstream).

* **Local delivery: third-party courier APIs** - a provider interface (`ICourierProvider`: quote, create job, cancel, webhook status) for Uber Direct / DoorDash Drive; the local shipment model and normalized statuses already fit (a courier job maps to a `LocalDelivery` with an external id); needs per-job cost on the delivery and a fallback when no courier accepts.
* **Local delivery: real route optimizer** - plug a routing provider behind `IRouteOptimizer` (Google Route Optimization, OSRM/VROOM self-hosted): config `LocalDelivery:Optimizer:Provider` + key, time-window constraints from the window of each stop, driver start/end depot, traffic-aware ETA instead of the 30 km/h straight-line estimate.
* **Local delivery: driver payroll and cost tracking** - per-delivery and per-km driver cost, route cost vs fee paid; needs driver rates on the membership and a report.
* **Local delivery: native driver apps** - the PWA covers v1; native adds background location, push for new stops and better camera control.
* **Local delivery: live map for the seller** - the board refreshes periodically; a live map would stream coarse positions over the existing SSE hub (single node today; needs the broker mentioned in ORDERS.md for several nodes).
* **Local delivery: multi-day routes, partial-order deliveries, cash on delivery, geocoding** - routes are one driver and one day; a local delivery covers the whole unshipped order; payment is always taken by the marketplace; coordinates come from the marketplace (add an `IGeocoder` to resolve addresses in the portal).

* **Shipping: carrier pickup scheduling** - Shippo `/pickups` behind `IShippingProvider.SchedulePickupAsync(labels, window)`; a `Pickup` row per carrier/day/address, cancelled when its labels are voided, shown on the dashboard.
* **Shipping: insurance** - an `insured_value` on the quote request (Shippo `extra.insurance`) with the premium added to the label cost line in the ledger (`shipping_insurance` kind); claims stay in the carrier/Shippo dashboard.
* **Shipping: multi-piece shipments** - `ShippingLabel` -> `ShippingParcel[]` (one label and tracking number per parcel under one `Shipment` group); rates are requested per parcel, the delivered rule becomes "all parcels delivered".
* **Shipping: marketplace-paid return labels** - an order/product flag (`ReturnShippingPaidBy = marketplace`) that posts the label debit to a `Platform` expense journal instead of the seller; the `return.label_created` event already carries what the marketplace needs.
* **Shipping rules engine** - conditions (weight, destination, value, SKU, brand) -> actions (preset, carrier/service, insurance, hold) evaluated at quote time; today only profiles, presets and the recommended rate exist.
* **Shipping: batch manifests / SCAN forms** - Shippo `/manifests` per carrier/day/address, stored as a file, listed next to the labels; the pickup flow would attach to it.
* **Shipping: other providers** - `EasyPostShippingProvider` / `ShipEngineShippingProvider` behind the same interface (rates, purchase, refund, tracking); provider ids on `ShippingLabel.Provider` already separate them, the webhook route is `/shipping/webhooks/{provider}`-shaped.
* **Shipping: live Shippo verification** - run `tests/Solvelt.Api.ShippoTests` with a test token, then a live smoke test before launch (see the going-live checklist in `docs/SHIPPING.md`).
* **Local delivery: masked buyer phone (needs a relay number) - KNOWN DEVIATION FROM THE BRIEF.** The brief asks that the driver never sees the buyer's real phone if the orders module masks it. The orders module does not mask the delivery phone (it is the phone the marketplace supplies for fulfilment), and the portal has no relay/proxy number, so the driver app currently receives the real number in `tel:`/`sms:` links (decision L13), while the buyer's e-mail is never shown and everything is hidden once the stop is finished. Closing this needs a number-masking service (e.g. a Twilio/SignalWire proxy session per delivery with the driver and buyer as participants, created on route start and closed on delivery, with the proxy number returned in `contact.call`/`contact.sms` instead of the real phone). Until then sellers should only invite drivers they trust with customer phone numbers.

* **Catalog: field-level change feed** - the feed re-sends the whole listing on every change; a changed-fields hint (`changed: ["price","availability"]`) per version would let consumers skip re-indexing. Needs per-field versions (a `CatalogChange(listingId, version, fields)` table pruned after N days).
* **Catalog: sharded version counter** - all catalog-changing transactions serialize on one counter row (milliseconds each, fine for a seller portal). If write volume ever needs more, move to an epoch + per-shard sequence and let the cursor be a vector.
* **Catalog: exact availability and reservations** - only the availability *state* is published; publishing quantities would need a bump per reservation (or a separate high-frequency stock endpoint the marketplace polls for items in carts).
* **Catalog: PostgreSQL concurrency test** - the concurrent-burst test runs on SQLite (writers are serialized by the database lock); a Postgres run would exercise the counter row lock itself. Run the same test against a Postgres container before launch.
* **Content reports: appeals and reporter notifications beyond the event** - the marketplace decides how to tell the reporter; an appeal flow (`content/reports/{id}/appeals`) and automatic holds after N reports are not built.
* **Webhook signature v2** - sign `<ts>.<event id>.<event type>.<body>` so the `X-Solvelt-Event-Id` / `X-Solvelt-Event-Type` headers are covered too (today only `<ts>.<body>` is signed and consumers must read id and type from the body). Ship as a new `v2=` scheme next to `v1=` for a transition period; the signature itself is unchanged for now.
* **Portal-set public display name** - team members cannot yet set a public name; provider/driver names are derived from the sign-in address only when it holds two name tokens, else "Provider N" / "Your driver" (N14, M45). A name field on the membership would need a migration.
* **PostgreSQL concurrency tests for bookings** - the parallel quote-accept / hold tests run on SQLite, where writers are serialised by the database, so they pass even without the provider lock; an opt-in PostgreSQL run is needed to prove it.
